# Процесс работы со спецификациями

Разработка ведётся по спецификациям с помощью [OpenSpec](https://github.com/Fission-AI/OpenSpec). Документация,
спецификации, бэкенд, фронтенд и Telegram-бот (`tg_bot/`) лежат в одном репозитории, поэтому одна доработка — это одно
изменение OpenSpec и один pull request.

**Функциональные требования — это спецификации OpenSpec** в `openspec/specs/`. Отдельного документа с функциональными
требованиями нет, чтобы не дублировать одно и то же в двух местах.

## Уровни документов

- **Уровень:** Бизнес-требование `BR-xxx`. **Где:** `docs/business/requirements.md`. **Отвечает на вопрос:** Зачем это
  нужно бизнесу и пользователям
- **Уровень:** Функциональные требования. **Где:** `openspec/specs/<capability>/spec.md`. **Отвечает на вопрос:** Что
  система делает для тренера и клиента
- **Уровень:** Дизайн изменения. **Где:** `openspec/changes/<change-id>/design.md`. **Отвечает на вопрос:** Как
  реализуем: API, хранение, интеграции, изменения в бэкенде, фронтенде и боте (`tg_bot/`)
- **Уровень:** Архитектурное решение. **Где:** `docs/architecture/adr/`. **Отвечает на вопрос:** Почему выбрано именно
  так (решения, которые переживут одно изменение)

### Что куда писать

**В спецификацию (`specs/`)** — поведение, которое можно проверить снаружи:

- что видит и делает тренер в кабинете, клиент в боте;
- правила: роли и права доступа, статусы, ограничения;
- поведение API, на которое опирается фронтенд.

**В дизайн изменения (`design.md`)** — как это устроено внутри: модель данных, эндпоинты, фоновые задачи, интеграции,
разбиение на компоненты.

**В ADR** — решения уровня всей системы: стек, база данных, провайдеры.

**Макет интерфейса** кабинета тренера и Mini App — в файле Figma Design, разработка через Figma AI
([ADR 0009](architecture/adr/0009-ui-design-figma.md)). `design.md` изменения OpenSpec этот макет не заменяет.

**В модели данных** ([`docs/architecture/data-model.md`](architecture/data-model.md)) — актуальная логическая схема
PostgreSQL, отдельным файлом, диаграмма Mermaid `erDiagram`. Любое изменение постоянных моделей, полей или связей
обновляет этот файл в том же изменении. Имена сущностей — из глоссария, поле «В коде».

## Как делается доработка

Пример: дневник питания (BR-003).

### 1. Предложение

```text
/opsx:explore                       (по желанию) обсудить с ИИ
/opsx:propose add-nutrition-diary
```

ИИ создаёт `openspec/changes/add-nutrition-diary/`:

- `proposal.md` — зачем (BR-003), что меняется, какие части затронуты (backend, frontend, tg_bot);
- `specs/nutrition-diary/spec.md` — функциональные требования со сценариями;
- `design.md` — API, хранение, интеграция с AI-моделями, экраны кабинета, диалог в `tg_bot/`;
- `tasks.md` — задачи, сгруппированные по частям: backend, frontend, tg_bot.

Предложение проходит ревью в pull request. После мержа требования согласованы.

### 2. Реализация

```text
/opsx:apply
```

ИИ реализует задачи из `tasks.md` в `backend/`, `frontend/` и `tg_bot/`, отмечая выполненные. Сначала бэкенд фиксирует
API-контракт (OpenAPI), фронтенд генерирует по нему клиент, бот вызывает внутренний API Django. Реализацию можно вести в
той же ветке или отдельным pull request.

### 3. Архивация

После выкатки в prod:

```text
/opsx:archive
```

Требования из изменения переносятся в `openspec/specs/`, а изменение уходит в `openspec/changes/archive/`.
`openspec/specs/` всегда описывает систему такой, какая она есть в prod.

### Мелкие доработки

Рефакторинг, исправление ошибок и улучшения производительности, которые не меняют поведение для пользователя, делаются
без изменения OpenSpec.

## Полезные команды

| Команда                      | Что делает          |
| ---------------------------- | ------------------- |
| `openspec list`              | Активные изменения  |
| `openspec show <change-id>`  | Изменение целиком   |
| `openspec validate --strict` | Проверка формата    |
| `openspec view`              | Интерактивный обзор |

## Формат требований

Ключевые слова оставляем на английском — на них опирается разбор OpenSpec. Текст пишем по-русски.

```markdown
### Requirement: Подключение клиента по ссылке

Тренер SHALL иметь возможность выдать клиенту ссылку на Telegram-бота для подключения. Источник: BR-001

#### Scenario: Клиент подтверждает тренера

- **WHEN** клиент заполнил анкету и подтверждает привязку к тренеру по ссылке
- **THEN** одним запросом создаётся клиент с этими данными и привязкой к тренеру
- **AND** клиент появляется в списке в кабинете тренера
```
