# 0011. Слои домена внутри приложения Django

- **Статус:** Принято
- **Дата:** 2026-11-17
- **Уточнено:** 2026-11-21
- **Дополняет:** [ADR 0005](0005-tech-stack.md)

## Контекст

API кабинета — одно приложение Django на домен: `trainers` и `clients`. Представления обращались к моделям напрямую,
выдача токена жила рядом с классом аутентификации. Дальше в том же процессе появятся сценарии кабинета, Mini App и бота.
Им нужна одна и та же граница: HTTP не решает правила, сценарий не собирает запрос к базе.

## Рассмотренные варианты

1. **Оставить представления и модели.** Меньше файлов. Правило входа и отзыв токенов остаются там, куда их положили
   первым.
2. **Общий пакет `api/` над доменами.** Имя домена видно в пути пакета. Приложение Django тогда хранит только модели, а
   вход по HTTP лежит снаружи.
3. **Пакеты слоёв внутри приложения домена.** У каждого домена свои `api`, `dto`, `services`, `entities` и
   `repositories`. Корневой `config/urls.py` только подключает `api/urls.py` домена.

## Решение

Принимается вариант 3.

Приложение Django — домен. Внутри него шесть пакетов:

- `api` принимает HTTP и отдаёт JSON. Сценарий называется как представление: `ClientListView`,
  `ClientListResponseSerializer`. Сериализатор запроса — `{Имя}RequestSerializer`: он проверяет и приводит поля тела,
  представление читает `validated_data`;
- `dto` — неизменяемая команда сценария. Команда называется как представление: `ClientListDto`;
- `services` выполняет сценарий. Класс называется как представление: `ClientListService`, метод `run(self, params)`
  принимает DTO и возвращает сущность. Представление входит только через `run`. Сервис не вызывает другой сервис;
- `entities` — сущность и правило одной записи. Модуль `{имя}_entity`, класс `{Имя}Entity`;
- `repositories` переводит строку таблицы в сущность и обратно. Модуль `{имя}_repository`, класс `{Имя}Repository`.
  Перевод строки — метод `_to_entity`;
- `models` хранит таблицы. Каждая модель — отдельный модуль. Импорт — `from clients.models import Client`. У класса нет
  методов с правилами: нормализация и проверка живут в сущности.

Класс модели Django сохраняет имя из глоссария (`Trainer`, `Client`, `RefreshToken`): от него зависят миграции и адрес
админки. Класс сущности называется `{Имя}Entity`.

Пути кабинета — коллекции ресурсов: `POST /api/access-tokens`, `POST /api/refresh-tokens`, `GET /api/clients`.
Раскладка пакетов эти пути не меняет.

## Последствия

- Новый сценарий домена добавляется сервисом и DTO, а не методом представления.
- Админка сохраняет тренера сама.
- Отдельной версии URL нет. Контракт кабинета по-прежнему проверяется снимком OpenAPI.
