# 0006. Telegram-бот на aiogram 3

- **Статус:** Предложено
- **Дата:** 2026-11-10
- **Связанные требования:** BR-002, BR-003
- **Дополняет:** [ADR 0003](0003-monorepo.md), [ADR 0005](0005-tech-stack.md)

## Контекст

Клиент общается с Trenly в Telegram, а те же данные смотрит тренер в кабинете. Клиент, анкета, дневник питания, тренировки и рекомендации — один домен, он живёт в Django и PostgreSQL.

Помимо чата у клиента будет Mini App. Экраны Mini App и кабинет тренера вызывают API Django напрямую. Бот эти запросы не проксирует.

Нужно выбрать библиотеку бота, где лежит его код и как он обменивается данными с Django.

## Рассмотренные варианты

1. **Процесс внутри `backend/`** — management-команда на Django, прямой доступ к моделям. Меньше сетевых вызовов, но цикл чата делит процесс и деплой с API кабинета.
2. **Отдельный сервис со своей копией доменной базы и брокером** — aiogram хранит клиентов и дневник у себя, Kafka развозит изменения в Django. Два источника одних и тех же записей: кабинет и чат видят данные с лагом.
3. **Отдельное приложение `tg_bot/` на aiogram 3, связь по HTTP** — домен остаётся в Django. Бот знает только внутренний API и шаг текущего диалога.
4. **Та же схема папок с python-telegram-bot или pyTelegramBotAPI** — тот же разрез процессов, другая библиотека диалогов.

## Решение

Принимается вариант 3.

- В монорепозитории появляется приложение `tg_bot/` со своими зависимостями, сборкой и деплоем. Состав репозитория из ADR 0003 дополняется этой папкой.
- Библиотека — aiogram 3.
- Бот не импортирует модели Django и не подключается к PostgreSQL.
- Входящее действие и чтение данных бот отправляет HTTP-запросом во внутренний API Django. Клиент в запросе задаётся `telegram_user_id`.
- Текст, который нужно показать в чате, Django отдаёт через тот же API. Бот забирает его и вызывает Bot API. Токен бота хранится только в `tg_bot`.
- Запрос к внутреннему API содержит сервисный токен. Webhook бота проверяется `secret_token` Telegram.
- Локально бот забирает апдейты через polling. В окружениях Telegram вызывает webhook.
- Незавершённый шаг чата хранится в Redis. Записи клиента, дневника и рекомендаций в Redis не пишутся.
- Распознавание КБЖУ и совет дня выполняются в Django. Бот приносит фото и доставляет уже сохранённый текст.

## Последствия

- Перезапуск бота не останавливает API кабинета, и наоборот.
- Каждое действие в чате — вызов API. Контракт этого API фиксируется вместе с остальным API Django.
- Пока Django не подтвердил запись, бот не пишет пользователю, что она сохранена.
- Повторный апдейт Telegram не создаёт вторую запись: внутренний API идемпотентен по идентификатору апдейта.
- Фоновые задачи по-прежнему выбираются отдельно. Воркер записывает рекомендацию в Django, бот только отправляет её в чат.
- Когда Mini App станет каналом клиента, определение бота в глоссарии («единственный канал клиента») нужно обновить вместе с требованиями.
