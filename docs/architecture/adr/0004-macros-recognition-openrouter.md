# 0004. Распознавание КБЖУ по фото через OpenRouter

- **Статус:** Предложено
- **Дата:** 2026-11-09
- **Связанные требования:** BR-004, NFR-PRIV-004

## Контекст

Клиент отправляет в бот фото еды и получает оценку КБЖУ. Нужна мультимодальная модель, которая по фото определяет блюда, примерный вес порций и КБЖУ. Своя модель на старте не оправдана.

## Рассмотренные варианты

1. **OpenRouter** — единый API к моделям разных провайдеров; модель меняется настройкой, без переписывания кода.
2. **Прямой API Google Gemini** — та же модель, но привязка к одному провайдеру.
3. **Российские модели (YandexGPT, GigaChat)** — данные остаются в РФ, но качество распознавания еды нужно проверять.

## Решение

Распознавание КБЖУ идёт через [OpenRouter](https://openrouter.ai), модель — [`google/gemini-3.8-flash`](https://openrouter.ai/google/gemini-3.8-flash):

- поддерживает изображения, быстрая и недорогая ($0,825 за 1 млн входных токенов, $4,125 за 1 млн выходных — на ноябрь 2026);
- бэкенд отправляет сжатое фото и промпт с требованием ответить структурированным JSON: блюда, вес, калории, белки, жиры, углеводы;
- идентификатор модели задаётся в настройках окружения, чтобы её можно было сменить (например, на `google/gemini-4-argon` для более сложных случаев) без изменения кода.

Оценка стоимости: ~1,5 тыс. входных и ~300 выходных токенов на фото — около $0,0025 за распознавание, примерно $0,3 на клиента в месяц при 4 фото в день.

## Последствия

- OpenRouter и Google находятся за пределами РФ: отправка фото клиентов — трансграничная передача персональных данных. **До запуска E7 решение нужно согласовать с юристом** ([NFR-PRIV-004](../../nfr/privacy.md)). Снизить риск помогает отправка фото без идентификаторов клиента.
- Если согласовать не удастся — переход на российскую модель (вариант 3) через тот же интерфейс в бэкенде.
- Качество оценки проверяется метрикой «Точность КБЖУ по фото» ([метрики](../../business/metrics.md)).
