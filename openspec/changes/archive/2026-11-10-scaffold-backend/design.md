## Context

Контейнер API описан в [containers.md](../../../docs/architecture/c4/containers.md): Python, Django, Django REST Framework, папка `backend/`, база PostgreSQL. Стек принят в [ADR 0005](../../../docs/architecture/adr/0005-tech-stack.md). Версии зависимостей ADR не фиксирует: берутся актуальные стабильные и закрепляются в проекте.

Сейчас `backend/` пустая. Фронтенд, бот, хостинг и деплой в этот каркас не входят.

## Goals / Non-Goals

**Goals:**

- Локально запускается Django-приложение и подключается к PostgreSQL в Docker.
- Зависимости зафиксированы так, что повторная установка даёт те же версии.
- Доступны Django Admin и пустая OpenAPI-схема. Схему дальше будет читать кабинет тренера.
- Команды запуска записаны в README.

**Non-Goals:**

- Модели тренера и клиента, аутентификация, права доступа.
- Образ приложения, CI, окружения dev/stage/prod, логирование и мониторинг.
- S3, Redis, `frontend/`, `tg_bot/`.
- Новый ADR и правка C4: состав контейнеров не меняется, компонентов внутри API ещё нет.

## Decisions

### Инструмент зависимостей — uv

Проект живёт в `backend/pyproject.toml`, версии закрепляются в `uv.lock`. Интерпретатор — самая новая стабильная ветка Python, которую одновременно поддерживают выбранные релизы Django, Django REST Framework и drf-spectacular. На ноябрь 2026 Django 6.1 поддерживает Python 3.12–3.15; если библиотека схемы отстаёт, берётся максимальная общая ветка, а не последняя Python любой ценой.

`uv` ставит интерпретатор и даёт один lock-файл. `requirements.txt` без lock-файла не выполняет требование ADR фиксировать версии.

### Процесс Django на хосте, база в Compose

`compose.yaml` в корне репозитория поднимает только PostgreSQL. Позже в тот же файл добавятся остальные локальные хранилища, чтобы инфраструктура по-прежнему стартовала одной командой.

Само приложение на этом шаге запускается на хосте (`uv run python manage.py runserver`). Образ и деплой — отдельное изменение: их рано смешивать с установкой каркаса.

### Раскладка каталога

```text
backend/
├── pyproject.toml
├── uv.lock
├── .python-version
├── manage.py
├── .env.example
└── config/
    ├── settings.py
    ├── urls.py
    ├── wsgi.py
    └── asgi.py
compose.yaml
```

Пакет проекта называется `config`. Доменные приложения появятся со своими изменениями, сейчас заводить пустые apps не нужно.

Настройки читают переменные окружения (`DATABASE_URL`, `SECRET_KEY`, `DEBUG`). Пример значений для локального запуска — `.env.example`. Секреты в репозиторий не попадают. Для локального `DEBUG=1` допустим явный несекретный `SECRET_KEY` из примера; без `DEBUG` приложение не стартует со значением по умолчанию.

База: актуальный стабильный PostgreSQL, пользователь, пароль и имя базы `trenly` только для локального Compose.

### Каркас API

- Django Admin подключён по `/admin/`. Учётная запись администратора командой не создаётся: интерактивный шаг нечем проверить автоматически.
- DRF и drf-spectacular подключены. Схема отдаётся по `GET /api/schema/` и на этом шаге не содержит операций продукта.
- `GET /api/health/` возвращает `200` и JSON `{"status": "ok"}`. Это проверка живости процесса, не функция кабинета.

### Проверка

Тесты — встроенный раннер Django, без отдельного pytest, чтобы не расширять набор инструментов. Один тест запрашивает `/api/health/` и `/api/schema/`.

## Risks / Trade-offs

- Python 3.15 может быть новее, чем поддержка drf-spectacular. Тогда фиксация более старой ветки Python откладывает обновление, но каркас сразу собирается.
- Пустая схема всё равно попадёт в OpenAPI. Для кабинета это заготовка контракта, не обещание эндпоинтов.
- Приложение вне Docker проще отлаживать и иначе ведёт себя, чем будущий контейнер деплоя. Расхождение закроет изменение с образом.

## Migration Plan

Каталоги `backend/` и корень репозитория пустые с точки зрения кода. Миграции Django на этом шаге — только системные таблицы. Откат — удалить добавленные файлы и volume базы.
