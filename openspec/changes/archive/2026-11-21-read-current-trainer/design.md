# Design

## Context

См. `proposal.md`. Вход и обновление пары уже отвечают только `access_token` и `refresh_token`. JWT содержит `sub` и
`exp`. `TrainerTokenAuthentication` читает тренера, пускает только активного и кладёт в запрос `TrainerPrincipal`
с одним id. Имя и фамилия остаются на `Trainer` и в `TrainerEntity`. Отказ кабинета — `401` и
`{"detail": "Неверные учётные данные."}`.

Токен доступа живёт в памяти кабинета, токен обновления — в `localStorage`. После перезагрузки страницы имя из ответа
входа уже негде взять.

## Goals / Non-Goals

**Goals:**

- Отдать имя и фамилию тренера из токена доступа отдельным чтением.
- Сохранить проверку активного тренера на каждом запросе кабинета.
- Не менять тела `POST /api/access-tokens` и `POST /api/refresh-tokens`.

**Non-Goals:**

- Экран кабинета, инициалы в шапке и хранение имени в браузере.
- Телефон, пароль, статус и id в ответе. Ключ объекта вместо адреса фото.
- Занятия на сегодня и ссылка приглашения.
- Токен клиента Mini App и сервисный токен бота.

## Decisions

1. **Имя читается запросом, а не кладётся в пару токенов.** Альтернатива — добавить `first_name` и `last_name` в ответ
   входа и в JWT. После перезагрузки токен доступа пропадает, а имя в JWT устаревает, пока администратор правит тренера.
   Отдельное чтение видит актуальное имя и не меняет уже выданный контракт пары.
2. **Путь `GET /api/trainers/me`.** `me` — идентификатор тренера из токена, не глагол. Клиент не передаёт id и не может
   запросить другого тренера. `GET /api/trainers` был бы единственным числом среди коллекций: `GET /api/clients`
   возвращает массив. `GET /api/trainers/{id}` открывал бы чужой id. Позже путь с id не должен перехватывать литерал
   `me`.
3. **Ответ `200` и тело `{"first_name", "last_name", "photo"}`.** `photo` — адрес из хранилища `trainer_photos`, не ключ
   объекта. Пустое фото отдаётся как `null`. Локальный путь дополняется хостом запроса, чтобы кабинет на другом порту
   открыл файл Django. Адрес, который уже начинается с `http://` или `https://`, не меняется: без DEBUG это временная
   подписанная ссылка. Статус не отдаётся. Телефон и пароль не отдаются.
4. **Те же слои, что у списка клиентов.** `TrainerDetailView` собирает `TrainerDetailDto` с id из principal и хостом
   запроса, вызывает `TrainerDetailService.run` и сериализует `TrainerDetailResponseSerializer`. Репозиторий кладёт в
   сущность `row.photo.url`. Сущность по хосту запроса заполняет `photo_url`: пустое фото остаётся `null`. Сериализатор
   отдаёт это поле как `photo`. Principal по-прежнему хранит только id: аутентификация не начинает отдавать поля
   ответа. Если между проверкой токена и чтением строки не стало, представление отвечает тем же `401`.
5. **Отказ не отличается от других запросов кабинета.** Нет заголовка, не Bearer, токен обновления, просрочка, чужая
   подпись и блокировка остаются на `TrainerTokenAuthentication`. Текст `401` не меняется.

### Части

- **backend.** Представление, DTO, сервис и сериализатор ответа. Новой модели, миграции и зависимости нет. Сценарии
  спецификации покрываются тестами рядом с тестами входа. OpenAPI описывает `GET /api/trainers/me`, схему Bearer и
  поля `first_name`, `last_name`, `photo`.
- **frontend.** Экранов нет. Снимок `frontend/api-client/openapi.json` и типы обновляются командами из README. Пакет
  `dashboard/` не создаётся.
- **tg_bot.** Без изменений.
- **docs.** В `docs/architecture/c4/components.md` у компонента «Тренер» добавляется чтение своего имени. Новый ADR не
  нужен: слои и коллекции ресурсов остаются по ADR 0011, `me` — выбор этого пути. `docs/architecture/data-model.md` и
  глоссарий не меняются: полей и терминов не прибавляется.

## Risks / Trade-offs

- [Имя читается вторым запросом к той же строке, что и проверка токена] → запрос лёгкий, principal не раздувается полями
  ответа.
- [Администратор меняет имя, пока токен доступа ещё жив] → следующее чтение `GET /api/trainers/me` видит новое имя.
- [Литерал `me` когда-нибудь совпадёт с id] → id тренера числовой, путь фиксирован строкой `trainers/me`.
- [Одинаковый `401` не различает причину] → кабинет не подтверждает, чей токен пришёл и жив ли тренер.
